# 4.3 GET /regions and GET /varieties: group_by as an Endpoint

Labs 5 and 9 used `group_by` to answer "which varieties rate highest?" and print
the answer. These two endpoints answer the same kind of question and return
JSON instead.

## GET /regions

```rust
async fn get_regions(State(state): State<AppState>) -> ApiResult<BTreeMap<String, u32>> {
    let df = state
        .lazy()
        .filter(col("region").is_not_null())
        .group_by([col("region")])
        .agg([len().alias("count")])
        .collect()?;
    // ... turn the two columns into a map
}
```

Two decisions are visible here.

- **Missing regions are filtered out, not counted under `null`.** A JSON object
  cannot have a null key, and "wines with no region" is not a region.
- **The response is a `BTreeMap`.** `group_by` does not promise an output order,
  and a `HashMap` would serialise in a different order on every run. A sorted
  map makes the response byte-stable, which makes it cacheable and diffable.

**Contract — counts cover every wine that has a region, and nothing else:**

```rust
#[tokio::test]
async fn regions_counts_every_region_and_skips_missing_ones() {
    let (_, regions): (_, BTreeMap<String, u32>) = get_json("/regions").await;
    let expected: BTreeMap<String, u32> = [
        ("Burgundy, France".to_string(), 1),
        ("Mendoza, Argentina".to_string(), 2),
        ("Oregon".to_string(), 1),
    ]
    .into();
    assert_eq!(regions, expected);
    assert_eq!(regions.values().sum::<u32>(), 4);
}
```

The fixture has five wines and one has no region, so the counts must sum to four.

## GET /varieties

```rust
let df = state
    .lazy()
    .group_by([col("variety")])
    .agg([
        len().alias("count"),
        col("rating").mean().alias("avg_rating"),
    ])
    .collect()?;
```

This is the aggregation from the `report` subcommand, minus the top-10 limit and
the Markdown table.

**Contract — each variety reports its row count and its mean rating:**

```rust
#[tokio::test]
async fn varieties_report_count_and_mean_rating() {
    let (_, varieties): (_, BTreeMap<String, VarietyInfo>) = get_json("/varieties").await;
    assert_eq!(varieties.len(), 2);
    let red = &varieties["RED WINE"];
    assert_eq!(red.count, 4);
    assert!((red.avg_rating - 91.75).abs() < 1e-9);
}
```

## Something the endpoint reveals

Run `/varieties` against the real gold layer and one key is `""`: 334 wines with
an empty variety. The silver layer trims and upper-cases `variety`, but never
rejects an empty one. An aggregation endpoint shows data-quality problems that a
row-level export hides. Fixing it belongs in silver, not in the server. That is
the point of the medallion layers.

## Contract summary

| Section | Contract | Enforced by |
|---|---|---|
| GET /regions | counts cover every wine with a region; output order is stable | `regions_counts_every_region_and_skips_missing_ones` |
| GET /varieties | count and mean rating per variety | `varieties_report_count_and_mean_rating` |
